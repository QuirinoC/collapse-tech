# Infinite Pixelboard production deployment

`ContainerApp.json` is a resource-group-scoped ARM template for a self-contained production layer. It provisions a VNet-integrated Container Apps environment, Log Analytics, a continuously running Container App, user-assigned runtime and migration identities, RBAC-enabled Key Vault, TLS-only Redis with a private endpoint, and PostgreSQL Flexible Server on a delegated private subnet. Names, locations, registry IDs, image references, and product settings are parameters; the template contains no subscription or resource-group IDs.

`Program.cs` trusts one forwarded-header hop only from the template's `10.42.0.0/23` Container Apps infrastructure subnet. Keep that CIDR synchronized if the VNet layout changes; do not broaden it to arbitrary proxies.

The board's Redis compatibility contract is unchanged. Deploying this template does not rename, scan, flush, import, or recreate application keys. Existing `PixelBoard_MainBoard_*` board keys and streams must be copied only through a separately reviewed, non-destructive cache migration if adopting this stack around an existing cache.

## External Azure prerequisites and blockers

These are deliberately outside the template because they require tenant, DNS, billing, or security-owner decisions:

1. Register `Microsoft.App`, `Microsoft.OperationalInsights`, `Microsoft.ManagedIdentity`, `Microsoft.KeyVault`, `Microsoft.Network`, `Microsoft.Cache`, and `Microsoft.DBforPostgreSQL` in the target subscription. Confirm regional quota for Container Apps, Redis, PostgreSQL Flexible Server, private endpoints, and the requested SKU.
2. Create an Azure Container Registry and retain its full resource ID and login server. The template grants only `AcrPull` to the runtime identity at that exact parameterized scope.
3. Create a GitHub Entra application or user-assigned identity with a federated credential restricted to this repository's `production` environment. Store its client, tenant, subscription, and object IDs as GitHub environment **variables**, not secrets. Grant it resource-group `Contributor`, plus only the ability to create the template's role assignments (`Microsoft.Authorization/roleAssignments/write`) at the target resource group and supplied ACR. A custom role is preferred over `User Access Administrator`. The template grants that exact object `Key Vault Secrets Officer` on the new vault so it can create and rotate deployment secrets; it receives no access to other vaults.
4. Configure GitHub's protected `production` environment with required reviewers and branch restrictions. Add the environment secrets listed in the workflow. Secret values must never be committed or placed in plain parameter files.
5. Configure the production Firebase project, Google and Apple providers, authorized domains, and the Container App FQDN/custom domain.
6. Create and validate the App Store products, App Store Server Notifications V2 URL, bundle ID, and Apple root certificate. Production accepts only the `Production` StoreKit environment.
7. Configure custom DNS and a managed certificate after the first deployment if the generated Container Apps hostname is not the public production name. Private PostgreSQL and Redis DNS are provisioned inside the stack VNet.
8. Confirm PostgreSQL zone-redundant HA is available in the selected region and that zones `1` and `2` are a valid pair; it is enabled by default. Override the HA parameters only after documenting the reduced availability. Decide whether the region also requires zone-redundant Container Apps, Redis Premium, or geo-redundant backup.
9. GitHub-hosted deployment requires the new Key Vault's public endpoint while RBAC limits access; the template does not add broad firewall bypasses. A private-only Key Vault requires a VNet-connected self-hosted runner plus a separately reviewed Key Vault private endpoint/DNS change. The first deployment may need one retry after the new Secrets Officer assignment propagates.

## Parameters and secrets

Use an immutable image such as `registry.azurecr.io/pixelboard@sha256:...`; `:latest` is prohibited by the workflow. Public product identifiers are parameters. The following values enter ARM as `secureString` values and are written to purge-protected Key Vault:

| Secret | Consumer |
| --- | --- |
| PostgreSQL administrator password | Migration-only connection; never exposed to the app |
| PostgreSQL runtime connection string | Runtime role with DML-only grants |
| Abuse-signal HMAC key | `Security__AbuseSignalHmacKey` |
| Apple root certificate | `StoreKit__TrustedRootCertificates__0` |
| Redis access key | Generated by Azure and written directly to Key Vault |

Firebase token validation needs only the project ID; do not deploy a Firebase Admin key. Advertising identifiers are not secrets, but all three operational switches default off. Never enable `Advertising__WebEnabled` or `Advertising__MobileEnabled` before `Advertising__ModerationOperationsEnabled` truthfully represents staffed moderation and working shutdown procedures.

The runtime identity can read Key Vault secrets and pull the image. The migration identity can read the migration connection secret but is not attached to the application. The runtime database role must never own the database, schema, migrations table, or DDL.

## OIDC deployment

Set these protected GitHub environment variables:

`AZURE_CLIENT_ID`, `AZURE_PRINCIPAL_OBJECT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`, `AZURE_LOCATION`, `AZURE_ACR_NAME`, `AZURE_ACR_RESOURCE_ID`, `FIREBASE_PROJECT_ID`, `STOREKIT_BUNDLE_ID`, `STOREKIT_MONTHLY_PRODUCT_ID`, `STOREKIT_ANNUAL_PRODUCT_ID`, `ADSENSE_PUBLISHER_ID`, `ADSENSE_BOARD_SLOT_ID`, `ADMOB_APPLICATION_ID`, and `ADMOB_MAX_CONTENT_RATING`.

Set these protected environment secrets:

`POSTGRES_ADMIN_PASSWORD`, `POSTGRES_RUNTIME_CONNECTION_STRING`, `ABUSE_SIGNAL_HMAC_KEY`, and `STOREKIT_TRUSTED_ROOT_CERTIFICATE`.

Run **Deploy Infinite Pixelboard** manually and explicitly choose the StoreKit and advertising feature switches. Advertising enablement fails closed when its protected identifiers are absent or operational moderation is not asserted. The workflow logs into Azure by OIDC, builds only `apps/infinite-pixelboard`, pushes a commit-addressed image, validates the ARM template, then deploys the exact image digest. It creates a distinct Container Apps revision for each workflow run, including configuration-only rollouts, and retries the initial deployment while a new Key Vault role assignment propagates. It does not use publish profiles, registry passwords, client secrets, or repository-wide Docker contexts.

For a local operator, authenticate with `az login`, select the intended subscription explicitly, and use `az deployment group validate` followed by `az deployment group create`. Pass secure values interactively or from a secret manager; never persist them in shell history or a checked-in parameters file.

## Migration and first enablement

Migrations are a separate release gate and must run from a trusted one-shot runner with network reachability to the VNet (for example, an approved self-hosted runner or temporary Container Apps Job). The runner assumes the migration identity, reads only `postgres-migration-connection-string`, and applies every file in `Infrastructure/Postgres/Migrations` in lexical order with `ON_ERROR_STOP=1`.

Before the first app rollout, connect as the migration owner and create a distinct login:

```sql
CREATE ROLE pixelboard_runtime LOGIN PASSWORD '<generated-secret>';
GRANT CONNECT ON DATABASE pixelboard TO pixelboard_runtime;
\c pixelboard
GRANT USAGE ON SCHEMA pixelboard TO pixelboard_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA pixelboard TO pixelboard_runtime;
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA pixelboard TO pixelboard_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE pixelboard_migrator IN SCHEMA pixelboard
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pixelboard_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE pixelboard_migrator IN SCHEMA pixelboard
  GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO pixelboard_runtime;
```

Create `POSTGRES_RUNTIME_CONNECTION_STRING` from that role. Apply migrations before deploying a revision that depends on them. Do not run migrations in application startup, do not give the runtime identity the migration secret, and do not roll schema backward destructively. Redis board keys and data are not part of schema migration.

## Backup, PITR, and restore drills

PostgreSQL automated backups and point-in-time restore are retained for 35 days by default. Enable geo-redundant backup only after confirming regional support and cost. Redis is live board state, not a substitute for a backup; select a Redis tier with persistence/export before launch if the recovery objective requires it.

Quarterly, restore PostgreSQL to a **new** server at a timestamp before a known test write, attach it to an isolated VNet/test revision, run `/health/ready`, compare row counts and entitlement/report samples, record RPO/RTO, and delete the drill resources only after evidence is retained. Never restore over production. Test Redis export/import against a disposable cache and verify representative `PixelBoard_MainBoard_*` keys, TTL-free board values, outbox consumer groups, and pixel serialization before any cache cutover.

## Secret rotation

1. Add a new Key Vault secret version and update dependent external credentials first.
2. For the runtime PostgreSQL role, use a transactionally coordinated password change and connection-string secret version. Restart a single test revision and require readiness before shifting traffic.
3. Rotate Redis keys one at a time: switch the Key Vault secret to the secondary key, restart and verify, regenerate the primary, switch back if desired, then regenerate the secondary. Never flush or replace the cache.
4. Rotate the abuse HMAC key only with a documented compatibility window because historical hashes will change.
5. Replace Apple trust anchors only after validating the new chain. Keep advertising switches off during uncertain configuration.
6. Revoke old versions after workload restart and audit confirmation. Key Vault purge protection remains enabled.

## Health, alerts, rollout, and rollback

Container Apps probes use `/health/live` for process liveness and `/health/ready` for Redis and PostgreSQL readiness. Configure Azure Monitor alerts routed to an owned action group for: zero healthy replicas, revision provisioning failure, sustained 5xx/latency, readiness failures, Container App restarts, Redis server load/memory/connections, PostgreSQL CPU/storage/connections/replica lag, Key Vault access failures, and Log Analytics ingestion gaps. Add an external HTTPS synthetic check for `/health/live` and `/health/ready`.

For staged release, first validate and migrate, then deploy an immutable digest with advertising kill switches off. Although the steady-state template uses single-revision mode, an operator may temporarily switch to multiple revisions, create a no-traffic revision, verify logs and both health endpoints, then move 1%, 10%, 50%, and 100% traffic with an observation window at each step. Return to single-revision mode after stabilization.

Rollback means routing traffic to the previous healthy immutable revision or redeploying its digest. Database changes must be expand/contract compatible with both revisions; roll forward to repair data or schema rather than running destructive down migrations. If Redis health fails, stop rollout and reconnect to the existing cache—never flush, rename, or bulk-delete board keys.
